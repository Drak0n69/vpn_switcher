# vpn_switcher

Бот для **персональной рассылки свежих Amnezia VPN-конфигураций** после переноса VPN-сервера на другой хост/IP.

Кирилл уже автоматизировал перенос сервера: после поднятия на новом хостере пользовательские `.vpn`-файлы пересоздаются с новым IP. Поэтому этот проект **больше не меняет Endpoint внутри конфигов**. Его задача теперь проще и безопаснее: взять готовые свежие файлы, проверить привязки и отправить каждому пользователю только его конфигурации в личный Telegram-чат.

## Как выглядит новый флоу

```text
ТСПУ блокирует текущий сервер
        ↓
Кирилл переносит/восстанавливает AmneziaWG на другом хостере
        ↓
серверная автоматика пересоздаёт все *.vpn
        ↓
бот видит папку с новыми конфигами
        ↓
recipients.yml связывает файл с конкретным Telegram-пользователем
        ↓
/status или /distribute показывает предварительную проверку
        ↓
/confirm <код>
        ↓
каждый файл уходит только владельцу в личку
        ↓
опционально в общей группе появляется обычное уведомление без файлов
```

**В общую Telegram-группу `.vpn`-файлы бот не отправляет.**

---

## Что хранится в Git, а что нет

В публичном репозитории должны лежать только код, Docker-файлы и примеры конфигурации.

Никогда не коммитим:

- реальные `*.vpn` и `*.conf`;
- `.env` с токеном Telegram-бота;
- `data/recipients.yml` с реальными `chat_id`/`user_id`;
- `runtime/registrations.yml`;
- `runtime/delivery_state.json`.

Для этого в проекте есть `.gitignore`. Если GitHub Web не загружает скрытый `.gitignore`, в архиве также лежит `gitignore.txt`: загрузите его и затем переименуйте в `.gitignore`.

## 1. Регистрация пользователей

Каждый пользователь один раз открывает бота **в личном чате** и отправляет:

```text
/start
```

Бот сохраняет Telegram `user_id` и `chat_id`, а пользователю показывает его `user_id`.

Пример ответа:

```text
Регистрация сохранена.
Ваш Telegram user_id: 123456789

Администратор привяжет к нему ваши VPN-конфигурации.
```

Простая регистрация **не даёт доступ ни к одному конфигу**. Файл будет отправляться только после явной привязки администратора в `recipients.yml`.

Администратор видит регистрации командой:

```text
/registrations
```

---

## 2. Первый запуск администратора

Для первого старта можно оставить `ADMIN_USER_IDS` пустым.

Создайте `.env`:

```bash
cp .env.example .env
```

Укажите токен:

```env
TELEGRAM_BOT_TOKEN=123456:replace_me
ADMIN_USER_IDS=
```

Запустите бота и отправьте ему в личку:

```text
/start
```

Он покажет ваш `user_id`. После этого впишите его в `.env`:

```env
ADMIN_USER_IDS=123456789
```

и перезапустите контейнер:

```bash
docker compose up -d
```

Можно указать нескольких администраторов:

```env
ADMIN_USER_IDS=123456789,987654321
```

---

## 3. Привязка пользователей к конфигам

Скопируйте пример:

```bash
cp data/recipients.example.yml data/recipients.yml
```

Заполните реальными значениями:

```yaml
recipients:
  - name: "Denis V."
    user_id: 123456789
    chat_id: 123456789
    files:
      - "denis-v(pc)_config.vpn"
      - "denis-v(android)_config.vpn"

  - name: "Ivan"
    user_id: 987654321
    chat_id: 987654321
    files:
      - "ivan_config.vpn"
```

Имена файлов у всех могут быть разными. Один пользователь может иметь один или несколько конфигов.

Можно использовать относительные подпапки:

```yaml
files:
  - "denis/pc.vpn"
  - "denis/android.vpn"
```

Пути с `..`, абсолютные пути и выход за пределы папки конфигов запрещены.

Бот также проверяет, что:

- один и тот же `user_id` не указан дважды;
- один и тот же `chat_id` не указан двум людям;
- один и тот же `.vpn` не назначен двум разным пользователям;
- пользователь действительно ранее зарегистрировался через `/start`;
- `chat_id` в `recipients.yml` совпадает с тем, который бот получил при регистрации.

Это снижает риск случайно отправить чужой конфиг не тому человеку.

---

## 4. Папка с автоматически созданными VPN-конфигами

По умолчанию Docker использует:

```text
data/configs/
```

Если после переноса Amnezia создаёт конфиги в другой папке, укажите её в `.env`:

```env
HOST_CONFIG_DIR=/absolute/path/to/generated/configs
```

Compose примонтирует её в контейнер **только для чтения**.

Например:

```text
/srv/amnezia/generated/
├── denis-v(pc)_config.vpn
├── denis-v(android)_config.vpn
├── ivan_config.vpn
└── ...
```

Бот не изменяет эти файлы.

## 5. Запуск

Перед первым `docker compose up` обязательно создайте `data/recipients.yml`.

```bash
docker compose up -d --build
docker compose logs -f
```

## Команды бота

Обычному пользователю:

```text
/start    зарегистрироваться
/whoami   показать свой Telegram user_id
```

Администратору:

```text
/registrations   показать зарегистрированных пользователей
/status          проверить регистрации, привязки и наличие файлов
/distribute      сформировать preview будущей рассылки
/confirm CODE    подтвердить рассылку
/help            показать команды
```

`/distribute` **ничего сразу не отправляет**. Сначала бот покажет сводку и выдаст одноразовый код подтверждения на 10 минут.

Пример:

```text
Проверка рассылки:
• получателей: 12
• файлов к отправке: 18
• без изменений: 0
• отсутствующих файлов: 0
• файлов без владельца: 0

Для запуска: /confirm a1b2c3
```

После `/confirm` план строится заново, чтобы между preview и отправкой нельзя было незаметно подменить состояние файлов.

## Проверки перед рассылкой

Бот проверяет:

- существует ли каждый файл из `recipients.yml`;
- имеет ли он расширение `.vpn`;
- не выходит ли путь за пределы `CONFIG_DIR`;
- зарегистрирован ли получатель;
- совпадает ли его зарегистрированный `chat_id`;
- нет ли одного файла у двух владельцев;
- есть ли `.vpn`, которые лежат в папке, но никому не назначены.

Если хотя бы один ожидаемый пользовательский файл отсутствует, массовая рассылка блокируется.

Файлы без владельца отображаются в preview, но сами никуда не отправляются.

---

## Защита от повторной рассылки

После успешной отправки бот сохраняет SHA-256 файла в:

```text
runtime/delivery_state.json
```

Если при следующем запуске файл для этого пользователя не изменился, по умолчанию он повторно не отправляется.

Настройка:

```env
SKIP_UNCHANGED=true
```

Если нужно принудительно переслать все файлы ещё раз:

```env
SKIP_UNCHANGED=false
```

после чего перезапустите контейнер.

---

## Уведомление в общей группе

Необязательно можно указать ID общей группы:

```env
ANNOUNCEMENT_CHAT_ID=-1001234567890
```

После успешной персональной рассылки бот напишет туда только сообщение вроде:

```text
VPN-сервер обновлён. Свежие конфигурации отправлены пользователям ботом в личные сообщения.
```

Сами `.vpn` в группу не прикладываются.

## Первый тест

Сначала используйте **тестовые пустышки**, а не настоящие пользовательские конфиги.

1. Создайте Telegram-бота и запустите проект.
2. Два тестовых аккаунта отправляют боту `/start`.
3. Администратор получает их ID через `/registrations`.
4. В папку конфигов кладутся два безопасных тестовых файла с расширением `.vpn`.
5. В `recipients.yml` каждому аккаунту назначается свой файл.
6. Выполняется `/status`.
7. Выполняется `/distribute`.
8. Проверяется preview.
9. Выполняется `/confirm CODE`.
10. Проверяется, что каждый аккаунт получил **только свой** файл.

И только после этого стоит подключать реальную папку, в которой Amnezia автоматически генерирует пользовательские конфигурации.

## Переход с первого MVP

В первой версии проекта бот сам менял `Endpoint` внутри `.vpn`. После новых вводных это больше не основной сценарий: свежие конфиги уже создаются при переносе сервера.

Если старые файлы ещё лежат в репозитории, их можно удалить:

```text
app/cli.py
app/healthcheck.py
app/switcher.py
app/telegram.py
app/vpn_config.py
tests/test_vpn_config.py
data/output/
```

Новая основная логика находится здесь:

```text
app/bot.py
app/distributor.py
app/scanner.py
app/storage.py
```
